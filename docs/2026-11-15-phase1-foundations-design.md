## 1. Интенция и защо

PetCare е за реални клиники и ще се хоства като multi-tenant SaaS. Фаза 1 поставя основата, върху която виси всичко останало:

- Никой без акаунт не влиза.
- Всяка клиника вижда **само своите** данни — на ниво заявка, не на ниво „не забравяй да филтрираш“.
- **Операторът (собственикът на системата) няма достъп до данните на клиниките.** Това е изрично решение на собственика: няма имперсонация, няма суперадмин-преглед на пациенти/записи/фактури. Операторският панел показва само метаданни.
- Чувствителните данни са криптирани при запис (лентата на „Аз и Ти“).
- GDPR основи: съгласие, изтриване с fan-out, реален privacy текст.

Защо сега: ClinicId трябва да е в всяка таблица ПРЕДИ останалите фази — следващото добавяне върху системата без изолация значи пре-факториране на всичко по-късно.

## 2. Цели / Не-цели / Анти-цели

**Цели:** Clinic таблица + ClinicId навсякъде; Identity с роли; операторски панел (само метаданни); криптиране; headers/CSP/rate limiting; connection string от конфигурация; audit log; GDPR основи (съгласие + erasure); изолационни тестове; GitHub Actions.

**Не-цели (тук, не в тази фаза):** Stripe/абонаменти (Фаза 5), поддомейни (използваме claims; поддомейн вариант се преоценява при нужда), имейл потвърждение на акаунти (за пилота не; преди публичен старт), 2FA (backlog), UI редизайн (Фаза 6), медикаменти/фактури.

**Анти-цели (какво би било провал дори да „работи“):**
- Оператор да може да прегледа съдържателни данни на клиника.
- Клиника А да прочете един ред данни на клиника Б.
- Master ключ в кода/git; PII в логове; patient данни в операторския панел.

## 3. Approaches (обсъдени и избрани)

### 3.1 Изолация по клиники
- **Избрано:** глобален EF Core query filter (`HasQueryFilter`) върху всички tenant таблици + scoped `ICurrentClinic` сервис, който чете ClinicId от claims на логнатия потребител. Service-ите НИКАК не приемат ClinicId като параметър от контролера — винаги от `ICurrentClinic`.
- Отхвърлено: ръчни WHERE проверки във всеки метод — един пропуск = теч; не се поддава на автоматична проверка.
- **Deny-by-default:** ако `ICurrentClinic` няма ClinicId (оператор, не-логнат), tenant заявките хвърлят изключение. Метаданните за оператора се четат от отделен, изрично ограничен сервис.

### 3.2 Криптиране и търсене
- **Избрано:** AES-256-GCM през EF ValueConverter (пряк пренос на `EncryptionService` от AzITi) върху чувствителни полета; търсенето на пациенти/стопани става в паметта върху вече tenant-филтрирания набор.
- Отхвърлено: deterministic encryption за търсими полета — по-слабо обещание за сигурност; по-късно, при реална нужда, добавяме хеш-колони за точно търсене.
- Мащаб: клиника = стотици до няколко хиляди пациента → in-memory филтър е незабележим.

### 3.3 Роли и оператор
- **Избрано:** ASP.NET Identity, роли `ClinicAdmin`, `Vet`, `Receptionist`, `Operator`. Операторът е същото Identity потребител с роля `Operator` и **без ClinicId**. Защитата не се разчита на ролята, а на deny-by-default (3.1) — оператор физически няма контекст, от който да тегли tenant данни.
- Отхвърлено: Google OAuth — не е практичен за служителски акаунти в клиника (за разлика от AzITi, където потребителите бяха Google-потребители по дефиниция); отделна оператор-инсталация (пре-инженерство за сега).
- Регистрация (публична): само създаване на **нова клиника** → ClinicAdmin акаунт. Vet/Receptionist акаунти се създават от ClinicAdmin изцяло в интерфейса.

### 3.4 Миграция на базата (от database-first към EF Migrations)
- **Избрано:** EF Core Migrations с baseline: `dotnet ef migrations add InitialBaseline` → в генерирания `Up()` се изпразва тялото → `dotnet ef database update` записва ред в `__EFMigrationsHistory` без да изпълнява нищо (каноничната рецепта за съществуваща БД). След това всеки преход е нормална миграция.
- Отхвърлено: ръчни SQL скриптове — няма история, няма rollback, лесно се разсинхронизира с модела.

### 3.5 Connection string
- **Избрано:** `OnConfiguring` + `#warning` от `VetClinicContext` се махат; единственият източник е `Program.cs` → `builder.Configuration.GetConnectionString("DefaultConnection")`. Dev стойността отива в user-secrets; prod — env var. (Днес програмата вече чете от конфигурация, но context-ът има закодирано дублиране — премахва се дублирането.)

### 3.6 Служителите и каталогът Veterinarian (от builder check)
- **Проблем:** прегледите/записите сочат FK `VetId` към таблицата `Veterinarian`, а служителите вече са Identity потребители — два разединени свята.
- **Избрано:** свързване 1:1. При създаване на Vet акаунт от ClinicAdmin системата създава и linked `Veterinarian` ред (за специализация/работно време, които не принадлежат на Identity). `ApplicationUser.VeterinarianId` (nullable; Operator/ClinicAdmin/Receptionist = null). `VetId` върху записите остава FK към `Veterinarian` — историческите записи НЕ осиротяват при деактивиране на служител (user → IsActive=false, profile-редът остава).
- Отхвърлено: директен FK от записите към ApplicationUser — историческите записи се чупят при изтриване/деактивация на акаунти; отделен каталог без връзка — потребителят „избира лекар“ на ръка при всеки запис.
- Дефолт: когато Vet прави запис/преглед, `VetId` по подразбиране = неговият linked profile (може да смени, само ClinicAdmin/Vet).

## 4. Модел на данните (промени в тази фаза)

**Нови таблици:**
- `Clinic`: Id, Name (≤100), Address?, Phone?, LogoPath?, CreatedAtUtc, IsActive (bool), BillingStatus (enum: Trial / Active / PastDue / Suspended / Cancelled), BillingPaidUntilUtc?, BillingProblem? (причина за неуспешно плащане, текст от провайдъра), TrialEndsAtUtc?
  - Билинговите полета се създават СЕГА (схема), пълнят се във Фаза 5. Така Фаза 5 не пипа tenant таблиците.
- `AuditLog`: Id (long), ClinicId?, UserId?, Action (кратък код, напр. `login.failed`, `patient.created`, `record.updated`, `clinic.deleted`), Entity?, EntityId?, AtUtc. **Без PII в съдържанието; без IP адреси** (IP = лични данни; добавяме по-късно със собствена retention политика, ако дойде нужда).
- Identity: `ApplicationUser : IdentityUser` + ClinicId? (null само за Operator) + DisplayName + `VeterinarianId?` (линк 1:1 за Vet роли — виж 3.6). Roles таблиците на Identity.

**Промени в съществуващи:** `OwnerId-колоната ClinicId` се добавя на: Owner, Patient, Appointment, MedicalRecord, Vaccination, Veterinarian. Всички нови редове задължително с ClinicId (non-nullable след миграцията). Миграция: съществуващите редове се привързват към пилотна клиника (Id=1, „Пилотна клиника“).

**Криптирани полета (ValueConverter):**
- Owner: FullName, PhoneNumber, Email, Address.
- Appointment: Reason (може да съдържа здравна информация — „повръща от 2 дни“).
- MedicalRecord: Diagnosis, Treatment, Notes.
- Veterinarian: PhoneNumber, Email (лични данни на служители).
- НЕ криптираме: Patient.Name (име на животното — слабо идентифициращо; за търсимост), Vaccination.VaccineName, имената на видове/породи (Фаза 2).
- Колоните стават `nvarchar(max)` (криптирани payload-и са по-дълги — като в AzITi).

## 6. Сигурност — конкретни стойности (пренос от AzITi)

- **Ключ:** `Encryption:MasterKey`, Base64, точно 32 байта; fail-fast при стартиране, ако липсва/е невалиден. Dev: `dotnet user-secrets`; prod: env var. Никога в git.
- **Бисквитки:** HttpOnly, Secure=Always, SameSite=Lax, 8 ч sliding expiration; login rate limit: 10 опита/мин на IP (429 при надвишаване); Identity lockout: 5 грешни опита → 15 мин блокиран акаунт; пароли: мин. 8 символа с главна, малка и цифра.
- **Headers (само production):** `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, строг CSP (копие на AzITi: `default-src 'self'; img-src 'self' https:; style-src 'self' 'unsafe-inline'; script-src 'self' 'unsafe-inline'; font-src 'self'; connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'; object-src 'none'`), HSTS, HTTPS redirect. Компромисът `unsafe-inline` за style/script е документиран (views-те имат inline блокове) — nonce-вариант е по-късен кръг.
- **Логове:** забранено е ILogger на пътища с PII; audit log съдържа само кодове и id-та.
- **Antiforgery:** MVC tag helpers по подразбиране; проверка, че нито един POST не е без токен.
- **Зад proxy (подготовка):** `UseForwardedHeaders` конфигурируемо (включено само когато приложението е зад reverse proxy, напр. nginx/Cloudflare/Azure Front). Без това per-IP rate limiting-ът вижда само IP-то на proxy-то → масови 429. Решението VPS/Azure е напречно, но кодът е готов и за двете.
- **Регистрация (гейт):** публичният Register е зад configuration toggle `Features:PublicRegistration` (**default: изключено**). Пилотните клиники се създават от операторския панел; при Фаза 5 toggle-ът се включва.
- **Bootstrap на първия Operator:** при стартиране, ако няма Operator потребител — създава се от конфигурация (`Operator:Email` + `Operator:InitialPassword`, env vars); в лога се извиква внимание за ротация на паролата. Никаква default парола в кода.
- **Пароли на staff акаунти:** ClinicAdmin въвежда начална парола сам в формата (изпълнява политиката за сила парола); показва се на служителя лично. Задължителна смяна при първи вход → backlog (без имейл потвърждение няма лесен self-service път).

## 7. GDPR (основите в тази фаза)

- **Съгласие:** при регистрация на клиника — отметка с реален текст; записват се `ConsentGivenAtUtc` + `ConsentTextVersion` на Clinic реда. Отметката се валидира на сървъра (не само required атрибут) — урокът от privacy-audit-а на AzITi.
- **Privacy страница:** реален текст (оператор, какви данни, къде се пазят, retention, права). Без placeholder адреси.
- **Erasure:** „Изтрий клиниката“ (ClinicAdmin, двойно потвърждение с въвеждане на името) → ErasureService fan-out: Appointments → MedicalRecords → Vaccinations → Patients → Owners → Identity потребители на клиниката → Clinic ред. Audit запис `clinic.deleted` (без съдържание). Данните изчезват истински — не soft-delete.
  - Изтриване на отделен стопанин: **блокирано, ако има пациенти** — изрично решение, което променя днешното поведение. Внимание: днес `DeleteOwner` каскадно изтрива пациентите им с цялата им мед. история (мълчалива загуба на данни — анти-цел по GDPR стила ни). Ново: блокирано с обяснителен екран; първо се изтриват/преместват пациентите.
- **Retention:** медицинските записи се пазят докато клиниката съществува (конфигурируеми N години след последното посещение — самата политика е задача на по-късна фаза; в privacy текста се описва реалното състояние).

## 8. Операторски панел (минимален за Фаза 1)

- Маршрут `/Operator/*`, политика само за ролята `Operator`.
- Вижда: списък клиники — име, статус на абонамента, дата на регистрация, брой пациенти/записвания (агрегатни числа).
- Може: деактивиране/активиране на клиника (IsActive), създаване на пилотна клиника + първи ClinicAdmin (provisioning без преглед на данни).
- НЕ вижда: пациенти, записи, фактури, стопани, причини — нищо съдържателно. Няма имперсонация. Архитектурно: панелът ползва само ограниченият metadata сервис; опит за tenant заявка = изключение.
- **Деактивиране на клиника (IsActive=false) — незабавен ефект:** отказ на нови входове + прекъсване на живите сесии (проверка на статуса при всяка заявка, cache ≤ 1 мин). Клиниката вижда ясен екран: „Акаунтът на вашата клиника е деактивиран — свържете се с поддръжката“. Причина: това е единственият реален спусък на оператора преди Фаза 5, значи трябва да действа мигновено, не при следващия logout.

## 9. План на миграцията (ред на стъпките)

1. Чистене: connection string в конфигурация; махане на дублирането в `VetClinicContext`.
2. EF Migrations baseline (рецепта 3.4) върху съществуващата БД.
3. Таблица Clinic + Identity (ApplicationUser, роли) — миграция.
4. ClinicId на шестте таблици + обратно пълнене към пилотна клиника (Id=1) — миграция.
5. `ICurrentClinic` + глобални query filters + пренос на service-ите (никакъв ClinicId от контролери).
6. Криптиране: EncryptionService + ValueConverters (тук старите текстови стойности се пре-криптират в миграция — еднопътен преход, отбелязан в документа на миграцията).
7. Identity UI: Register (създава клиника + ClinicAdmin; зад toggle), Login, staff management при ClinicAdmin (създава Vet/Receptionist/още ClinicAdmin; Vet акаунт → linked Veterinarian ред; начална парола от админа).
8. Операторски панел (минимален) + забрана за tenant достъп.
9. Audit log + GDPR (consent, erasure, privacy страница).
10. Headers/CSP/rate limiting/lockout/пароли + `UseForwardedHeaders` (конфигурируемо).
11. Тестове: изолация (две клиники, кръстосан достъп = отказ на ниво service), криптиране (roundtrip + tamper), erasure fan-out, lockout, headers (WebApplicationFactory). Тестовете тичат срещу **реален SQL Server**: локално — ephemeral тестова база (уникално име на изпълнение) срещу SQLEXPRESS/LocalDB; CI — SQL Server service container в GitHub Actions. SQLite/in-memory е отхвърлена — не репликира query filter-ите и FK семантиките, които тестовете уж доказват. GitHub Actions: build + test.

Всяка стъпка = отделен commit; развалящо-себе-ми стъпки (5 и 6) се правят последователно, не едновременно.

## 10. Критерии за приемане

- [ ] Две клиники с данни; от една НЕ се вижда нищо от другата — доказано и с автоматични изолационни тестове.
- [ ] Операторски акаунт: списък с метаданни работи; опит за достъп до tenant данни = отказ.
- [ ] Деактивирана клиника: жива сесия прекъсва ≤ 1 мин; нов login е отказан; показва се обяснителен екран.
- [ ] Директна SQL заявка: чувствителните полета са нечетим payload.
- [ ] Грешни пароли → lockout; headers/CSP видими на живо; грешна карта не е приложимо още (Фаза 5), но BillingStatus полетата съществуват в схемата.
- [ ] „Изтрий клиниката“ → нула редове останали; audit записът остава.
- [ ] GitHub Actions: зелен build + тестове.
